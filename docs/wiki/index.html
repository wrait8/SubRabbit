Sub Rabbit MK.II Wiki

Sub Rabbit MK.II is an ESP32 + CC1101 sub‑GHz multitool, controlled over a serial CLI and a companion web UI. This wiki covers hardware setup, the full command reference, and feature‑by‑feature guides.

⚠️ Read this first: this device can transmit, jam, and brute‑force sub‑GHz RF. Only use it on equipment you own or are explicitly authorized to test, and make sure your use complies with your local radio/telecom regulations. See Legal & Responsible Use.

Getting Started

What you need

  • An ESP32 dev board (the firmware calls SET_LOOP_TASK_STACK_SIZE, which is ESP32‑Arduino‑core specific).
  • One CC1101 sub‑GHz transceiver module ("Module A"). A second CC1101 ("Module B") is optional and only needed for dual‑module features — see Dual‑Module Setup & RollJam.
  • The Arduino IDE (or PlatformIO) configured for your ESP32 board, with the ELECHOUSE_CC1101 library available, plus the project's own sources (cli.*, WebInterface.*, radio_manager.*, eeprom_layout.h, and the RF driver / recorder / player / signals / jammer / analyzer modules the CLI delegates to).

Wiring

Signal Module A (required) Module B (optional)
SCK GPIO 18 shared bus
MISO GPIO 23 shared bus
MOSI GPIO 19 shared bus
SS / CS GPIO 5 GPIO 25
GDO0 GPIO 2 GPIO 26
GDO2 GPIO 4 GPIO 27

Both modules share the same SPI bus (SCK/MISO/MOSI); only CS/GDO0/GDO2 are per‑module. If you're wiring only one module, use the Module A pins — the Module B pins are simply left unconnected and firmware never touches them unless you explicitly ask it to (see below).

Board note: on many ESP32‑WROVER boards, GPIO16/17 double as PSRAM pins. Module B's pins were chosen to avoid probing anything unsafe, and module‑B detection is deliberately not run at boot — it only runs when you issue the modules command (or press "Check Modules" in the web UI).

Flashing

  1. Open the sketch (SubRabbit.ino) in the Arduino IDE / PlatformIO.
  2. Select your ESP32 board and the correct serial port.
  3. Build and upload.

First boot

  1. Open a serial monitor at 115200 baud, newline = CR or LF.
  2. On boot you should see: ``` CC1101 OK Sub Rabbit MK.II - type 'help' for available commands

    `` If you instead seeCC1101 err, double‑check your wiring and that the module is getting power — the firmware callsELECHOUSE_cc1101.getCC1101()` right after init and reports the result.

  3. Run help to see the full command list (also documented in CLI Command Reference).
  4. The device also starts its own Wi‑Fi access point (web.begin()) — see Web Interface for connecting from a browser.

Basic workflow

> freq 433.92        # set frequency (MHz)
Freq: 433.92 MHz
> rx                  # start the sniffer
RX started
> stop                # stop whatever mode is active
All stopped
> status              # see current mode/buffer state
Rx:OFF Jam:OFF Rec:OFF Chat:OFF Armed:OFF Frames:0 Buf:0 Echo:ON

From here, head to Recording & Playback or Raw Capture & Replay depending on whether the remote you're working with uses the CC1101's packet engine (decoded frames) or needs raw edge‑timing capture.

CLI Command Reference

Commands are sent as plain lines over serial (115200 baud) or via the web UI's command queue, and are parsed by CommandHandler::processLine() as <command> [args]. Unknown commands print Unknown: <command>.

This page documents every command implemented in cli.cpp, including a few that exist in the parser but aren't listed in the in‑firmware help text (marked undocumented in help below).

Web Interface

Sub Rabbit MK.II hosts its own Wi‑Fi access point and web UI via the WebInterface class, instantiated in SubRabbit.ino and driven from loop() (web.loop()) alongside the serial CLI. The CLI and web UI share the same CommandHandler backend, so anything you can do from serial you can do from the browser, and vice versa.

The WebInterface implementation itself isn't included in this pass of the repo — this page documents what's observable from how cli.cpp and SubRabbit.ino use it. Expand this page once WebInterface.* lands.

What the CLI tells us about it

  • web.begin() is called once in setup(), after cli.setWebInterface(&web) wires the recorder/player/signals modules and the CLI itself to the same WebInterface instance.
  • Connected‑client log streaming — CommandHandler::logPrint() mirrors every CLI log line to the web client via web->sendLog(msg, type) when a client is connected (web->isClientConnected()), so the web UI gets a live log feed in addition to whatever direct Serial output it sees.
  • .sub file push — subexport sends the exported .sub text to a connected web client via web->sendSubFile(text), in addition to printing it over serial. This is the recommended path for large captures — subimport over serial is explicitly limited to short blobs.
  • AP settings — apset <ssid> <pass> persists the new credentials to EEPROM and then calls web->restartAP(ssid, pass), which restarts the access point under the new SSID/password. You'll need to reconnect your phone/laptop to the new network afterward.
  • "Check Modules" button — the Settings page's "Check Modules" button maps to the modules CLI command (CommandHandler::cmdModules()), which actively probes for a second CC1101 and re‑initializes Module A as a side effect (see CLI Command Reference). The dashboard's passive module/role display should use modstatus instead, since that reads cached state without touching hardware.
  • Command queue — cmdRollJam()'s source comments note it's often reached from web->loop() (web UI → command queue → CLI), which is why it deliberately avoids calling web->loop() again inside its own wait loop (to avoid recursive stack growth on a pending command).

Connecting

  1. After boot, look for the device's Wi‑Fi access point (default SSID/ password are whatever your WebInterface build ships with — change them any time with apset <ssid> <pass> from the CLI or the Settings page).
  2. Connect your phone or laptop to that AP.
  3. Open the device's web UI in a browser (check WebInterface's default address, typically the ESP32 SoftAP gateway IP, e.g. 192.168.4.1, unless configured otherwise).
  4. The dashboard should mirror serial log output and give you the equivalent of the CLI commands above through buttons/forms.

Large .sub captures

If you're exporting a raw capture with a lot of pulses, prefer the web UI: subexport streams the full .sub text to a connected browser client, while the serial subimport <sub-text> path is sized for short blobs only.

Recording & Playback (decoded frame buffer)

This is the "packet engine" workflow: frames the CC1101 itself has decoded (as opposed to raw edge timing — see Raw Capture & Replay).

Recording

> rec
Recording started

rec toggles recordingMode on, turning off any other active mode (RX sniff / jam / chat), selects the module for RX, and puts the radio in RX mode. While recording, CommandHandler::handleRx() (called every loop() iteration) pushes every successfully decoded packet into the recorder's frame buffer via recorder.addFrame().

Toggle it off with rec again, or with stop (which also stops RX/jam/chat and aborts any in‑progress raw capture).

Adding frames manually

> add DEADBEEF
Frame added. Total: 1

add <hex> accepts a hex string (up to 120 hex characters / 60 bytes), converts it to bytes, and appends it directly to the buffer — useful for hand‑crafting a frame without actually receiving it over the air.

Inspecting the buffer

> show      # list buffered frames
> status    # Frames:<n> Buf:<bytes used>, among other state

Clearing the buffer

> flush
Buffer flushed

Playback

> play 2     # replay frame #2 (1-indexed)
> play       # replay every frame in the buffer, in order

play <N> maps to player.playFrame(N-1) (converted to 0‑indexed internally); play with no argument calls player.playAllFrames().

Persistence

> save   # write the frame buffer to EEPROM
> load   # read the frame buffer back from EEPROM

The frame buffer's EEPROM region is separate from the fixed‑code signal region and the AP‑credentials region — see eeprom_layout.h and EEPROM_SIGNAL_REGION_OFFSET / EEPROM_AP_REGION_OFFSET for the layout, so saving one doesn't clobber the others.

Raw Capture & Replay

Raw mode captures the actual edge timings on the air (via a GDO0 interrupt, attached inside recorder.init()), independent of the CC1101's packet engine. This is what you want for signals that don't fit a configured packet format, or before you know what protocol you're dealing with.

Arming a capture

> recraw s          # arm immediately, no RSSI gate
> recraw s -65       # arm, but wait for RSSI to cross -65 dBm first

The RSSI gate is opt‑in. Bare recraw s arms right away with no threshold — this matches the tool's original pre‑RSSI behavior. Only recraw s <dBm> waits for that RSSI level before capturing; picking an unreachable threshold will otherwise silently time out and look like nothing happened, so start without a threshold if you're not sure.

Stopping / status

> recraw x    # stop and decode the ISR capture
> recraw ?    # print ISR capture status

Seeding a capture manually

> addraw +100,-200,+150,-300,...
Edge data added (4 pulses)

addraw accepts an edge pulse train directly — positive numbers are "high" durations, negative numbers are "low" durations, in microseconds. This is the only manual raw‑ingest path; a previous hex‑interval variant has been removed. It's handy for replaying a train you captured elsewhere (e.g. pasted from a .sub file or another tool).

Replaying

> playraw

Replays the last edge capture, whether it came from an ISR capture or from addraw.

Decoding

> decode

Runs the decoder against the last capture (same decode step recraw x triggers automatically).

Where this feeds into other features

  • Fixed‑code signals (recsig) builds on the same ISR capture machinery but additionally tries to match the result against the known protocol registry — see Fixed‑Code Signals.
  • .sub export (subexport) exports whatever is in the raw edge buffer — see .sub File Import/Export.
  • KeeLoq (keeloqtest) looks for KeeLoq‑shaped framing in the last raw capture — see KeeLoq.
  • lastcapture gives you a quick summary (pulse count, decode result if any) without re‑running anything.

Fixed‑Code Signals

Sub Rabbit MK.II includes its own protocol‑registry‑based encoder/decoder for common fixed‑code remotes (as opposed to rolling‑code systems like KeeLoq — see KeeLoq). It's a from‑scratch implementation (the code comments note it deliberately doesn't depend on the RCSwitch library).

Capturing and decoding a signal

> recsig
Waiting for signal (ISR capture + decode)...
Loaded: code=1234567 bits=12 te=320us

recsig runs an ISR capture (same mechanism as raw capture, with no RSSI gate) and tries to decode it against the protocol registry. If no protocol match is found, you'll see:

No confirmed fixed-code signal captured.

On success, the decoded (protocol, code, bits, TE) tuple is stored as the "loaded signal" for the session.

Inspecting the loaded signal

> showsig
Protocol: Came  Code: 1234567  Bits: 12  TE: 320us

Replaying the loaded signal

> playsig

Re‑transmits the loaded signal using its recorded protocol/timing.

Persisting the loaded signal

> savesig    # write loaded signal to its own EEPROM region
> loadsig    # read a signal back from EEPROM

The fixed‑code signal lives in its own EEPROM region (EEPROM_SIGNAL_REGION_OFFSET), separate from the frame buffer's region, so savesig/loadsig won't collide with save/load.

Brute forcing a protocol

If you don't have a captured signal but know (or are testing) a protocol from the built‑in table, see Brute Force for sweeping the full code space instead of decoding a captured one.

Brute Force

brute <protocol> [freq] [repeats] sweeps the entire code space of a known fixed‑code protocol's timing table, transmitting every possible code in sequence.

> brute came 433.92 1
Brute Came 433.92MHz x1
0/4095
10/4095
...
Brute force done

Built‑in protocol timing table

Protocol Bits Code space
Came 12 4,096
Nice 12 4,096
Ansonic 12 4,096
Holtek 12 4,096
Linear 10 1,024
Chamberlain 9 512

Protocol name matching is case‑insensitive. If you pass an unknown name:

> brute foo
Unknown protocol

freq defaults to 433.92 MHz and repeats defaults to 1 if omitted.

What it does under the hood

For the duration of the sweep, the radio is taken out of its normal packet mode (setCCMode(false), setPacketFormat(3)) and bit‑banged directly on the TX GPIO pin using the protocol's pilot/zero/one/stop pulse timings, then restored to packet mode afterward. Progress is logged every 10 codes.

Stopping a sweep

Send any character over serial (Serial.available()), or run stop — both set an internal stop flag that the sweep checks between codes:

Brute force stopped

Notes

  • This transmits continuously across the protocol's entire code space at the configured power and frequency. See Legal & Responsible Use before running this against anything you don't own or aren't explicitly authorized to test.
  • The web UI's web->loop() is pumped once per code during the sweep so the web connection stays responsive while a sweep is running.

.sub File Import/Export

Sub Rabbit MK.II can export and import Flipper Zero‑compatible RAW .sub text, so captures can move between this tool, Flipper Zero, and other compatible tooling.

Exporting

> subexport

Exports the last raw capture (the edge pulse buffer from raw capture) as .sub text:

  • Prints the .sub text over serial.
  • Also pushes it to a connected web client via web->sendSubFile(), which is the recommended path for large captures.
  • If a fixed‑code signal was decoded from the same capture, its protocol name, code, bit count, and timing (TE) are embedded alongside the raw pulses.
  • If there's nothing to export: text No raw capture to export - run recraw first

Importing

> subimport RSSI: ... (sub-text here)
  • subimport <sub-text> parses the given .sub blob, loads its pulses into the edge buffer, and sets the device's frequency from the file's embedded frequency.
  • If the file carries the extended protocol fields (protocol name + code + bits + TE) and the protocol name matches an entry in the fixed‑code registry, the decoded signal is loaded too (equivalent to what recsig produces), ready for playsig.
  • Serial import is sized for short blobs only. For large captures, import via the web UI instead: text Usage: subimport <sub-text> (or use the web UI for large captures)

Typical round trip

> recraw s
> recraw x
> subexport
# copy the printed .sub text, or receive it in the web UI
# ... later, on the same or another device ...
> subimport <paste the .sub text>
> playraw

KeeLoq

Sub Rabbit MK.II includes KeeLoq frame tooling for testing systems you already have the key for (e.g. your own remote/receiver pair during development, interoperability testing, or key‑recovery‑free protocol analysis). The source comments are explicit that the cipher core is exact but the on‑air (OTA) frame timing is best‑effort and may need tuning per device — see keeloq.h in the firmware for notes.

KeeLoq is a rolling‑code scheme used in many vehicle and gate/garage remotes. Interacting with a KeeLoq system you don't own or aren't explicitly authorized to test is illegal in most jurisdictions and can affect safety‑relevant equipment. See Legal & Responsible Use.

Decoding a captured frame

> keeloqtest <key_hex>
  • Takes a hex key (up to 16 hex digits / 64 bits).
  • Looks for KeeLoq‑shaped framing in the last raw capture (see Raw Capture & Replay — run recraw first).
  • On success, reports the frame's serial, button, and counter fields (the key is assumed correct for this decode — it isn't independently verified against a known‑good counter sequence): text [+] KeeLoq frame: serial=0x1234567 button=3 counter=42 (key assumed correct)
  • On failure: text No KeeLoq-shaped framing found in the last capture (header/PWM timing may need tuning - see keeloq.h notes)

Building and transmitting a frame

> keeloqtx <key_hex> <serial_hex> <button 0-15> <counter>

Builds a KeeLoq hopping‑code frame from the given key, serial, button, and counter value, and transmits it.

Troubleshooting

If keeloqtest consistently fails to find framing on a capture you expect to be KeeLoq, the issue is most likely header/PWM timing tuning rather than the cipher itself — see the notes in keeloq.h.

Dual‑Module Setup & RollJam

Dual‑module ("Module A / Module B") support

A second CC1101 is optional. With one wired up, you can assign TX and RX to different physical modules — which is required for RollJam (below) and can be useful any time you want to transmit and receive simultaneously on different settings.

Wiring Module B

Signal GPIO
SS / CS 25
GDO0 26
GDO2 27

SCK/MISO/MOSI are shared with Module A (18/23/19).

Detection is manual, by design

Module B is never probed automatically at boot. Some of its pins double as PSRAM pins on certain ESP32‑WROVER boards, so probing them unconditionally isn't safe on every board. Detection only runs when you explicitly ask for it:

> modules

This: 1. Actively probes for Module B. 2. Re‑initializes Module A (rf.init()) afterward, to guarantee it comes back in a clean state regardless of how Module B's probe affected the shared SPI bus's CS/MISO tri‑state behavior. This resets frequency/modulation/etc. back to defaults — re‑apply your preset after running modules. 3. Reports the result: text Module B: present | TX: Module A | RX: Module A

If you just want to read the current cached state without touching hardware (e.g. for a dashboard that polls on load), use modstatus instead — it never probes and never resets Module A.

Assigning TX/RX modules

> txmodule a|b
> rxmodule a|b

Both require Module B to have been detected first (modules), and persist the assignment to EEPROM via radioMgr.saveToEEPROM().

RollJam (experimental)

This feature is explicitly marked experimental and untested against real two‑module hardware in the source. Jam‑burst rate vs. capture‑idle‑gap detection timing will likely need tuning once validated on actual hardware. Treat it as a starting point, not a finished feature.

RollJam captures two consecutive presses of a remote while jamming the receiver, so each press can potentially be replayed later. It requires:

  • Module B detected (modules has been run and reports it present), and
  • RX and TX assigned to different modules (rxmodule/txmodule).
> rolljam start
[RollJam] EXPERIMENTAL - untested on real two-module hardware, timing may need tuning.
[RollJam] Press the remote now for slot 1...
[RollJam] Slot 1 captured: 143 pulses
[RollJam] Press the remote now for slot 2...
[RollJam] Slot 2 captured: 140 pulses
[RollJam] Done. 'rolljam replay1' opens now (unused code) - slot 2 stays banked for later.

Each slot is capped at ROLLJAM_SLOT_MAX pulses and has a 15‑second window to capture a press before giving up.

Replay either captured slot:

> rolljam replay1
> rolljam replay2

Abort an in‑progress sequence:

> rolljam stop

Notes

  • The RX module always captures and the TX module always jams — this is fixed for the duration of the sequence regardless of your general txmodule/rxmodule preference, then restored afterward.
  • If no signal is captured in a slot, the sequence aborts: text [RollJam] No signal captured for this slot - aborting.
  • RollJam interacts with real‑world access‑control systems (gates, garage doors, vehicles). See Legal & Responsible Use before testing this against anything you don't own or aren't explicitly authorized to test — and be aware that jamming is independently regulated/illegal in most jurisdictions regardless of what it's paired with.

Troubleshooting

Symptom Likely cause / fix
CC1101 err at boot Check SPI wiring (SCK 18 / MISO 23 / MOSI 19 / SS 5) and that the module has stable power. Reported immediately after ELECHOUSE_cc1101.Init() in CommandHandler::init().
recraw s <dBm> seems to hang / never captures An unreachable RSSI threshold will silently time out. Try recraw s with no threshold first to confirm capture works at all, then add a threshold once you know a reachable RSSI level.
Frequency/modulation/settings reset unexpectedly Running modules re‑initializes Module A as a side effect of checking for Module B, which resets RF settings to defaults. Re‑apply your preset/frequency after running modules. Use modstatus instead if you only need to read cached module/role state.
txmodule/rxmodule says "nothing to choose" Module B hasn't been detected yet — run modules first.
RollJam aborts with "No signal captured for this slot" The 15‑second capture window closed before the remote was pressed, or Module B/RX wiring needs attention. Also confirm RX and TX are assigned to different modules (RollJam requires this).
subimport prints "Usage: subimport ..." for a capture you know has data Serial subimport is sized for short blobs — use the web UI for large .sub imports.
Unknown: <command> Check spelling/case against the CLI Command Reference — command names are case‑sensitive.
tx/add says "Invalid hex" The hex string must have even length and be ≤120 characters (≤60 bytes).
Device won't respond to new serial input while a brute sweep is running Send any character on serial, or issue stop, to break out of the sweep — it checks for a stop condition between codes.
Web UI shows stale module/role info If the dashboard polls module status automatically, make sure it's calling modstatus (read‑only) and not modules (which actively probes and resets Module A) — this is a backend/wiring consideration, not something you toggle from the CLI.

If you run into something not covered here, please open an issue with the command sequence that reproduces it and the serial log output.

Legal & Responsible Use

Sub Rabbit MK.II can:

  • Transmit on sub‑GHz ISM bands (tx, playsig, playraw, rolljam replay*, keeloqtx, …)
  • Jam RF (jam, and as part of rolljam start)
  • Sweep the entire code space of several fixed‑code garage/gate remote protocols (brute)
  • Capture, decode, and replay signals from third‑party devices

In most countries:

  • Radio transmission is regulated by frequency, power level, and equipment certification. Confirm your local rules (e.g. ISM band limits) before transmitting anything.
  • Jamming any radio spectrum is independently illegal in most jurisdictions, regardless of what it's paired with or why.
  • Accessing, capturing, replaying, or interfering with RF systems you don't own (garage doors, gates, vehicle remotes, alarms, etc.) without the owner's explicit permission is illegal in most jurisdictions and can create real safety risks (e.g. interfering with access control or alarm systems).

Only use this project on equipment you own, or with explicit, documented authorization from the owner — for example, your own remotes/receivers, or an engagement you've been contracted/authorized to test. This project is intended for security research, interoperability testing, and education.
